# Compiler and SDK implementation stages

Deliver both overhauls as reviewable slices. The first shared proof is a fixture SDK bound call that runs through verified bytecode and uses an installed table in the verified interpreter. Lead with interpreter implementation and independent conformance. The compiler track can work on syntax and checked execution while the SDK track works on declarations and world loading. ## Dependencies and review checkpoints

- **Stage 0 → stage 1.** Start with the existing tree and release artifacts. The recorded no-compilation constraint still applies. Source inventory, test design and artifact inspection can proceed now. A build or executable verification gate that needs a new artifact remains pending until compilation is authorized.
- **Stages 2A and 2B can overlap.** Start stage 3 once the fixture resolves to an installed contract and the checked semantic adapter is available. Full AST conversion and complete world instantiation can continue alongside the interpreter slice. Finish AST parity before deleting its adapter.
- **Stage 4 has separate acceptance gates for layout and reuse.** Start the generic descriptor and reference layout before choosing inline shapes and niches. Keep physical reuse and cache retirement behind the scope release and loan decisions. Stage 5 can use reference layouts and bounded fixture inputs while that work is pending. Full scope correctness is required for cutover.
- **Interpreter conformance comes before stage 6.** Exercise resumable execution, the required storage and ownership contracts, and the first fixture bound call in the verified interpreter. Start native work against independently checked results and publish only functions with complete lowering and maps.
- **Check compacted scalar bytecode during stage 3.** Exercise relocated branches and backedges, and debugger markers at activation pauses. [No-op removal](backend-design.md#remove-executable-no-ops-before-interpreter-conformance)
- **Stages 7 and 8 share recovery metadata.** Start scheduler and bridge work once the image format is stable. Enable native stack copying only after all live stack references are accounted for. Enable loop OSR after import/export and commit-phase recovery work on an active frame.
- **Stage 9 is incremental.** Core supply, package migration, and removal of obsolete producers can land as their gates clear. Record deferred items individually. Resolving a public package choice does not change the verified bytecode or backend interface.
- **Stage 10 is a direct execution switch.** Implementation slices run independently before cutover. Test expectations come from language, runtime and SDK contracts. Any required operation the verified interpreter cannot execute blocks the switch. Native admission and recovery remain inside the new pipeline.

Before closing a stage, record the delivered behavior, exact revision/configuration, checks performed, and any skipped gate. Mark performance figures as measured or historical. Use the pending-decision records for authority on core, layout, source failure, SDK defaults, storage reuse, test remediation and repository policy. [Pending decisions](pending-decisions/README.md)

## First implementation slices

These slices are in the working tree following the data-enum baseline `d6ebc04` and the backend design revision `8e1cbef`. Release-profile runs cover the verified bytecode, CLI and scalar SDK fixtures. Workspace failures are tracked by name. [Regression record](pending-decisions/07-baseline-failures.md)

| Area | Working slice | Next integration gate |
| --- | --- | --- |
| AST | Ordinary source, REPL, file-graph and runtime module compilation now route user source through indexed syntax. File discovery uses indexed module declarations and passes its snapshots to compilation. Modern relinking retains static snapshots and materializes trees at the linker boundary. | Run parity, diagnostic and dynamic-load tests on the changed entry points and measure parse and check costs. Build tables directly during parsing and migrate core, resolution, generic instantiation and deferred checking before retiring the source-tree adapters. |
| Bytecode and interpreter | Opt-in verified scalar bytecode v8 with direct, bound and output call targets, the loop step check, explicit storage lifetimes, shared/exclusive scalar loans and borrowed calls. Programs that print integers, booleans and string constants run end to end: `cyallo run --engine verified` executes the entry routine and refuses anything it cannot lower before running. Format v9 adds composite registers: tuples and enums of scalars and nested composites, described by module shapes with an explicit variant index (the reference layout; inline shapes and niches stay with the layout decision). A composite owns its value and shares the register's storage lifetime, so loop rebuilds reuse one frame slot. Composites cross direct calls as parameters and results, but the entry routine stays scalar. Matching reads by value; payloads read by address are reference copies and writes through them, by-reference matches and loans of composites are refused. Composites are native-ineligible. Format v11 adds binary64 values (stored as bits), IEEE float arithmetic and comparison, checked integer and float negation, boolean `not` and equality, `i64`/`f64` conversion with typed out-of-range failure, and integer real division for CAIE `/`. Float output uses the shortest round-trip spelling. Float routines are native-ineligible. Format v12 adds immutable strings (`text`) and fixed-size arrays with inclusive per-dimension bounds, elements that start uninitialized when declared, checked indices, and character-based `len`/`LEFT`/`RIGHT`/`MID` with typed failures. Arrays are limited to 2^22 elements by the verifier. Text and arrays are native-ineligible. Mixed integer/real operands, other numeric widths, globals, records, function values and closures, loans of non-scalars, owned payloads (`rc`, `gc`), growable collections and tasks remain unsupported and block cutover (stage 6A). Priority is the Cyallo (`.ya`) language; CAIE support is incidental.

**Roadmap to run `examples/composites.ya`** (records, tuples of records and closures, by-value and by-reference closure capture):

1. *Records.* A record is a named-field tuple shape. Lower `Type::Record` to a shape and project nested fields (`pair.0.x`) as field-of-field places. Gate: `Point` fields print through a tuple.
2. *Function values and by-value capture.* A closure value is a composite of a routine id and captured values. Add a closure value type that carries its call signature, a construct instruction, and an indirect call that the verifier checks against the signature. Checked IR passes captures as leading parameters of the closure routine. Gate: `apply(offset_by(3), 4)` prints 7 and a closure survives being returned.
3. *Loans of any pointee.* Generalize loans beyond scalars to composites and closures, with the owner-lifetime and conflict rules the scalar loans already have. Gate: `&mut` and `&` parameters of tuples and records read and write fields in place.
4. *Loans stored inside values.* A closure may capture a mutable loan (`proc[&mut count]`). The verifier must keep the owner live and exclusive for as long as the closure value lives, and reject returning it. Add an indirect call through a loan to a closure. Gate: `count_twice()` prints 2 and the escaping variant is rejected.
5. *Gate for the whole example.* Output equals the documented lines under the verified engine, with typed failures and fuel preserved across pauses.

**Status.** Steps 1 and 2 are implemented (format v13). Records lower to named-field tuple shapes that keep their declaration identity, and nested field reads (`pair.0.x`) lower to value extracts. Closures are values with a module signature table, a construct instruction whose captures become the routine's leading parameters, and an indirect call checked against the signature. Closures work as parameters, results, tuple, record and array elements, and capture scalars, text and composites by value. Closures and records are native-ineligible. `composites.ya` runs completely on the verified pipeline. Writes through a field or payload address are still refused, since the register holds a copy.

Step 3 is implemented (format v14). A loan now carries its pointee type, so it can borrow a value of any type: scalar, text, tuple, record, enum, array or closure. Whole-value reads and replacement go through `ReadLoan` and `WriteLoan`. A loan can be projected to one field, enum payload or array element, from an owner or from another loan, and the projected loan keeps the root's origin and never has wider access than its base. Projected places are paths from the owning register, so they stay valid when frames move. The verifier rejects a projection whose pointee or access does not match its base, and rejects reading or reborrowing the owner while an exclusive projection lives. Reads from a local's field or payload still observe a copy, and writes through a local's field, nested field, loan parameter or projected loan are real in-place writes. Writes through a copy are refused when lowering. Projecting into a variant that is not held fails with a typed error.

The debugger runs on the verified session (format v35). Each routine image carries its source variables and where each lives (a frame register, or a module variable), and the verifier's storage facts say which registers hold a value before any instruction, so the session can show the variables of the innermost frame (and the entry routine's as `global::name` from other frames), the call stack by routine name, and the module variables; a variable with no value shows as `uninitialized`, and a value that handles point at is shown a few levels deep. Statement boundaries carry the debugger's stops: statements that produce no code share an instruction with the next one, so the session keeps a cursor over the statements that begin there and each is a stop of its own, which keeps stepping by line the way the older session did. `random` was added to the interpreter with the older generator's algorithm, seeded from the context, so a restart repeats a run. A restart clears the output. Programs the verified engine cannot lower yet cannot be debugged. `repl` still uses the legacy session.

The CLI `run` command now defaults to the verified interpreter (phase 3 of the cutover plan, for `run`). Output is written as it is produced, input is read from standard input when the program asks (a closed standard input fails the waiting instruction with the end of input), and a failure is a diagnostic with its code and source span, the same form as before. A JIT report, notices, `--jit-no-inline`, inspection output or an explicit `--engine jit|interpreter|cranelift|cranelift_speed` still use the legacy engines, and a program the verified engine cannot lower (it keeps a character or a 32-bit number, for example) falls back to the legacy tiered engine unless `--engine verified` was asked for. `repl` and `debug` still use the legacy session: the REPL replaces source while keeping state and the debugger reads statement boundaries, locals and the call stack, none of which the verified session offers yet.

Phase 2 of the cutover has started: `cyallo::vm::Session` runs a program on the verified interpreter with the surface of the older session (`new`, `with_context`, `run(budget)`, `step`, `restart`, `status`, `depth`, `current_span`, `instruction_count`, `program`, and the context's input queue and output string). A waiting input source lets the activation pause on an input instruction, which the session reports as `WaitingForInput` until a line is queued. Verified failures map to the older runtime errors where one exists (arithmetic, end of input, call depth, generator misuse) and otherwise to a verified failure variant with its message and a code of the same family, and the failing instruction's span. Test files that only run a program and read its output or status (`nesting`, `simplified`, `modern`, `effects`) now use it and give the same results. The rest of the 37 files fall into groups that are not a matter of repointing an import: tests that hand a running session to the legacy native backends (`composites`, `cells`, `constants`, `data_enums`, `managed_syntax`, `postfix_dereference`, `generators`, `managed`, `concurrency`, `lookups`, `namespace`, `parallel_compilation`, `dynamic_import`) compare engines and move to the verified native tiers or go with the legacy backends at the switch; tests of engine internals (`services`, `tiering`, `inlining`, `metrics`, `inspection`, `gc`, `debugger`, `object_fuzz`, `native_*`) assert counters and reports that only the legacy engines produce and need new expectations or removal at the switch.

Native functions held in erased values are implemented (format v34), which completes the examples. A native callable is a value of its own kind (`std::num::abs` as a value), and an erased call on one asks the compiler for an adapter, as the old runtime did: `specialize_calls` compiles a routine that calls the native function with the argument types the erased values carry and returns its typed result, the module is re-lowered with the adapter as an extra root under the same check as a module load, and the call runs the adapter in the caller's task with the result erased. The adapter for a function and its argument types is made once. Only integers, reals, booleans and strings have a checked type to compile for, so an erased call with other argument kinds, or arguments the function does not accept, is a typed `ObjectFault::Type` failure. Float absolute value was added to lowering because `abs` on a real needed it. `objects/views.ya` runs identically under `--gc-stress`. Every example in the repository now runs on the verified engine with the output the old interpreter gives, so the "refuses unsupported programs" CLI tests use a program that keeps a character (no verified representation yet).

Service contexts are implemented (format v33). Contexts, registrations, keys and live service references are values of their own kinds, and the interpreter keeps one table of contexts and provider bindings with the old runtime's states (active, retiring, inactive). A context sees the providers of its realm for each key; `isolate` gives one key a fresh realm, `extend` inherits, `provide` registers a trait object (a key has one provider per realm, a second is `ProviderConflict`), and a reference is a context and a key that resolves at every call, so a replaced provider is seen by existing references and a withdrawn one is `NotInjected`. `inject` runs a callback in a child context that is admitted to the provider the key resolves to now and keeps that binding; `on_dispose` registers cleanup. Disposing a registration or a context retires the binding or the context, collects the cleanups of everything admitted to it (children first, a provider's dependents before it) and runs them as ordinary frames in the old order, each frame tagged with the context it is cleaning up; a retired binding is released when no call is in flight (a method call holds a lease on its provider for the length of the call), no admitted context still lives and no cleanup frame of its owner is running. Disposal is idempotent and a disposed context fails new operations with `InactiveContext`. `services/main.ya` runs identically under `--gc-stress`, and `lookup-services/main.ya` and `services/main.ya` are the last services examples. Not implemented: slot and call-site caches (every call resolves through the tables), service statistics, and native-tier service views. With this, `objects/views.ya` is the only example that does not run on the verified engine (it calls a native function held in a `dynamic`).

Owned erased values, constant aggregates and count arithmetic are implemented (format v32), which is what the source-level registry in `lookup-services` needed. `Any` (`std::any::erase` and `checked`) holds a value of any type with its type, owns what it holds (so it is released, moved and cloned like an owner and may hold counted values), and `checked` takes the value back only as exactly the type it was erased from, a typed `ObjectFault::Type` failure otherwise. A constant aggregate (a record or tuple of constants, such as a frozen service key) is a per-routine table entry built whole. Counts (`usize` and `u64`) have checked arithmetic and comparison, and index vectors, arrays and storage paths. `or_fail(message)` unwraps like `unwrap` and reports the variant, not the message. Two lowering changes came with it: a routine may now take trait objects and generators by value, and a borrow of a temporary's slot that the checked IR places before the value is stored is moved to just before the loan's first use (only when the owner is written before then and the loan is not rewritten in between). `lookup-services/main.ya` runs identically under `--gc-stress`. 

Run-time module loading is implemented (format v31). A `load` call does what the old runtime did: it asks the loader and the program's compile plan for the module, compiles the extended program, and runs the namespace builder and the module initializers, here synchronously on the caller's turn. A verified module keeps the checked program it was lowered from; after a load it is re-lowered from the extended program with the namespace builder and initializers as extra roots, which lowers them after everything the entry reaches, so every earlier routine keeps its number. Before the new code replaces the old, the engine checks that every routine it already has is identical in it (instructions, registers up to appended unused ones, call sites, lists, texts, contracts, outputs) and that every table (shapes, signatures, managed types, traits, implementations, module variables) keeps its entries and their numbers; if not, the load fails with a failure value saying which part changed, so frames that are already running can never meet different code. Module variables grow to the new count, and a namespace is cached by load key so a second load of the same module returns the same object and initializers run once. `load` returns `Result<dynamic, LoadError>` and a view returns `Result<T, ViewError>`; both errors are one failure value with a message and the kinds not found, denied and failed checks. Erased calls (`module[name](21)`) check the callee's signature against the argument types, wrap the result as erased, and run in the calling task; exports read back with their types when a view requires them. `modules/dynamic/main.ya` and `concurrency/modules/main.ya` (two tasks that each load a module and call it) run identically under `--gc-stress`. Not implemented: callables that are native declarations held in a `dynamic` (`objects/views.ya` calls `std::num::abs` that way; the old runtime compiles an adapter for it), exported types and deferred generic callables in a namespace, and a load that would change running code, which is refused rather than handled. Loading compiles the whole program again, so a load costs as much as a compile.

Trait methods that take their receiver by value are implemented (format v30), which is what `modules/static` needed (`fn value(self)` on an imported trait). The method records that it takes a copy: the dispatch hands the routine a copy of what the object holds instead of a loan, so the object keeps its value and a second call sees it again. The verifier requires the implementing routine's first parameter to be the receiver type itself and that type to own nothing counted (it could not be copied out of a shared object). `modules/static/main.ya` runs identically under `--gc-stress`. Source modules themselves needed nothing new: the checked program is already linked.

Open objects and erased values are implemented (format v29). An object is a heap object that holds its properties (name, the value with the type it was stored with, and an optional required type), so objects share identity, are traced by the collector and may form cycles; a handle copy is the same object. A `dynamic` value is the value together with its verified type, and reading it back as a type checks that type (`ObjectFault::Type`). An object literal requires its properties to keep their types, a `dynamic { ... }` literal makes them configurable, an unknown property of an open type reads as `dynamic`, and a computed key reads and writes by name. Writing a required property with another type, deleting one, writing a readonly object and reading a missing property are typed `RunError::Object` failures. A view (`Named = object { name: string, .. }`) checks that the properties exist with those types and requires them from then on through every alias; freezing makes the object readonly through every alias. Erased arithmetic, comparison and boolean operators check the actual types and use the ordinary integer and float rules (checked overflow and division by zero), and a comparison may produce a plain boolean. The property sets live in a per-function contract table. Values that own counted or channel ends (`rc`, `weak`, senders, receivers, tasks, generators) cannot be erased or stored in an object, because an object could neither release nor move them; the verifier rejects them. `open.ya` and `native-ic.ya` run identically, also under `--gc-stress`. Not implemented: shape descriptors and per-site inline caches (every access searches the property list, so `native-ic.ya` runs correct but not fast), nested view requirements (a nested object requirement only checks that the property is an object), `std::object::view` and its `ViewError`, invoking a callable held in a `dynamic` (which compiles an adapter at run time and belongs with dynamic modules), and native-tier guards.

Tasks, joins, cancellation and clocks are implemented (format v28). A task is a frame stack of its own: the interpreter keeps the running task's frames on the activation's stack and the others in a task table, and switches by swapping stacks, so one activation runs many tasks cooperatively on one thread. A task runs until it blocks, ends, or has run 1000 instructions while another task is ready. A blocking operation that cannot finish (a send to a full channel, a receive from an empty open one, a join of a running task, a sleep that has not ended) leaves its program counter on itself and reports `Blocked`, which gives the turn to the next live task in round-robin order and is retried when the task is next scheduled. A receive that parks registers on its channel, which is how a zero-capacity send finds a waiting receiver. When every live task has been tried and none made progress the engine sleeps until the earliest sleeper wakes, or fails with `Deadlock` if nobody sleeps. `spawn` moves the closure's captures into the new task and refuses values that cannot cross (loans, handles, counted owners, generators, closures) with `NotTransferable`. `join` takes the outcome, an enum of completed (with the result, the unit value for a task that returns nothing), failed, cancelled and stopped; a task whose code fails reports failed and the parent goes on. `cancel` marks the task, which ends the next time it is selected and releases its frames' parameters, so a cancelled receiver's channel closes. A clock is a capability token and `sleep` takes milliseconds. Concurrency is cooperative and deterministic for a given program: unlike the old runtime nothing runs in parallel, tasks never overlap in time, and the interleaving of output from tasks that print depends on the quantum. All examples under `examples/concurrency` except `modules/main.ya` run identically, also in one-instruction slices and under `--gc-stress`. Not implemented: `stopped` outcomes (the entry task returning ends the activation with other tasks abandoned), the channel buffer quota, `select`, and task failure messages (a failed task reports only that it failed). A cancelled or failed task releases its parameters but not its locals.

Channels are implemented (format v27), without tasks yet. `Sender<T>` and `Receiver<T>` are identified by new `sender` and `receiver` type flags in the standard bindings and are counted owners of a channel in a table the interpreter owns: cloning adds an end, releasing the last sender closes the channel for receivers once the queue drains, and releasing the last receiver closes it and discards the queue. `close` on a sender keeps the queue, `close` on a receiver discards it. Send and receive build the declared `Result` values, with the variants located by their declared encodings (`SendClosed`, `SendFull`, `SendLimit`, `ReceiveClosed`, `ReceiveEmpty`), so a failed send hands its value back. A `Result<(), E>` now has a unit payload, and unwrapping a payload nobody can name checks only the variant. A blocking send or receive that cannot finish (the channel is full, or empty and open) is a typed `Deadlock` failure until tasks exist: with one task nothing else can serve it. A bounded channel holds its capacity plus one value per parked receiver, which is how a zero-capacity channel hands a value to a waiting receiver. `channels/buffered.ya` runs identically under `--gc-stress`. The buffer quota (`Limit` failures) is not modelled.

Owners held by a routine are released when it returns. The checked IR releases a local at the end of its scope, which an explicit `return` skips, and releases a parameter nowhere, so both stayed counted until the frame vanished (`strong_count` one too high after a call that took an `rc` it did not pass on). Lowering now appends a drop of every owned local and parameter before each return, when every path to that return has written the register. A drop of a value that was moved out releases nothing, so no move analysis is needed, and the lifetime pass keeps the register live up to the drop. A register written on only some paths to a return (for example a local declared inside a loop body, with a return after the loop) is still not released there. Counts now match the old interpreter on the cases tested (`tests/verified_release.rs`).

Generators are implemented (format v26). A generator is a value of its own kind that owns one suspended frame, held in a generator table the collector treats as a root. Its description (what it yields, what a resume passes in, what it returns) reuses the signature table. A routine that is a generator body carries that description; calling a closure of such a routine makes a generator over copies of the captures instead of running the body, so one factory makes independent generators. `start`, `next` and `resume` push the frame above the resumer, `yield` pops it back into the table and hands the resumer a step (the yielded value in the first variant, the returned value in the second), and a return completes the generator. The resume value is written into the register of the yield that suspended it. Loans of the frame's own registers follow it to its new stack index on every resume, so a borrow may live across a yield and be resumed from a different call depth; a generator body cannot take loan parameters. Starting twice, resuming before `start` and resuming a finished or closed generator are typed failures (`RunError::Generator`), and closing twice is allowed. Closing, or releasing the owner, drops what the suspended frame owns. `yield from` works because it is ordinary generator operations over a delegate. The three generator examples run identically under `--gc-stress` and in one-instruction slices. Owners are released at returns (see below).

Remaining blockers for cutover, as the verified lowering now reports them (the first unsupported item of each example): services need `ServiceKey<T>` values and generic service handles (`services/*`, `lookup-services`); . Each is a slice of its own; none is partially implemented. Both Cranelift profiles of the verified backend now request the backtracking register allocator explicitly.

Retained field locations and allocators are implemented (format v25). A `Location<T>` (identified by the `location` type flag in the standard bindings) is a value that refers to a field of a traced record: a place rooted in the heap object, so a collection keeps the record alive for as long as the location lives. `field(&owner, "name")` makes one from a handle or a loan of one, `load` copies the field (a counted owner inside gains an owner), `store` replaces it and releases the old value, and a clone is an alias of the same field. `Layout` is a size and an alignment, an `Allocation` is a token the engine does not account for, and `Allocate` always succeeds; an allocator that refuses (a failure variant passed to `rc(...)`) is a typed `AllocationRejected` failure. `rc(allocator) value` builds a counted object that remembers its allocator state and its deallocation routine. When the last owner is released the value is destroyed and the routine then runs as an ordinary frame with an exclusive loan of the allocator state and the allocation, between the instruction that released the owner and the next one; several owners released by one instruction are deallocated in release order, and a tuple or record releases its components last to first, as the old interpreter does. The block outlives the call while weak references remain, the allocator state is released once the routine returns, and the collector treats the state as a root. `locations.ya` and `managed.ya` run with the documented output under `--gc-stress`, so all 33 examples now run identically on the verified engine. Not implemented: allocator accounting and size limits, fallible `rc(...)` (a result instead of a failure), borrowed allocator receivers, and a location of a field of a counted owner (only traced records).

Storage paths and mapped lookups are implemented (format v24). A path is a value of its own kind: a list of projections (into a cell, handle or counted owner; into a record field; to a vector or array element), or the missing path. It holds indices only, never an object, so it needs no tracing and no destructor. `std::lookup::path(receiver)` starts the empty path, `target`, `field` and `element` append a step, and `missing` is the path that reaches nothing. `mapped(receiver, key, mapper)` is a call target: the mapper runs as an ordinary closure frame, so budgets, pauses and collection behave as for any call, and when it returns the path is applied to the receiver and the caller receives an option of a copy of what it reaches (a counted owner inside gains an owner). A step that does not fit its value, an element past the end and a negative index are typed failures (`RunError::Path`). The reached value is checked against the declared payload kind when the path is applied, because a path names its target by position only. `lookups.ya` runs with the documented output under `--gc-stress`, which makes 31 of the 33 examples identical to the old interpreter. Not implemented: the per-site lookup cache and its version guards (every call runs the mapper, which gives the same results for the readonly mappers the checker admits, but `lookup_stats` has no counterpart), the check that a path starts at the receiver it is applied to, and retained field locations (`Location<T>`). `managed.ya` (allocators) and `locations.ya` (locations) remain.

Interactive input is implemented (format v23). Two instructions read one line from an input source: `Input` writes a register and `InputLoan` writes through an exclusive loan, so both `INPUT n` on a local and `input(&mut answer)` through a borrow lower directly. A line is text (kept as typed), a 64-bit integer, a finite number, or `TRUE`/`FALSE` in any case; numbers and booleans ignore surrounding white space. The source is an `InputSource` set on the activation (the CLI default reads standard input), and each line is consumed exactly once however the run is sliced. End of input and a line that does not spell the requested kind are typed failures (`InputExhausted`, `InputInvalid`) with the old messages. `secret-number.ya` and `input.psc` now run identically, which makes 30 of the 33 examples identical to the old interpreter; `managed.ya` (allocators), `locations.ya` (locations) and `lookups.ya` (lookup plans) remain. Characters are not supported as an input type yet, and the native tiers still reject input.

Trait objects are implemented (format v22). An object is a value erased to a declared trait: boxing a value allocates a shared heap object holding it, and the object handle carries the implementation it was boxed for. Copies of the handle share the object's state, and the collector keeps it alive like any heap object. The module has a table of trait descriptions (each method's receiver access, parameters and result) and a table of implementations (the trait, the receiver type and one routine per method). The verifier rejects an implementation whose routine does not take a loan of the declared receiver type and access followed by the declared parameters, rejects a call to a method the trait does not declare, and checks that a boxed value has the implementation's receiver type. A method call looks up the routine in the object's implementation and passes a loan of the object's contents as the receiver. Lowering lowers every method of every implementation that some routine boxes a value for, so an unsupported method of such an implementation blocks the program. An address handed to a routine that takes a reference is now an implicit borrow of the local, which `tally.add(3)` needs. `traits.ya` runs with the documented output, with and without `--gc-stress`, which makes 28 of the 33 examples identical to the old interpreter. By-value receivers, trait objects in generic bounds and traits with by-reference parameters are not supported.

Standard intrinsics are implemented (format v21): explicit clone (counted owners inside gain an owner, handles keep their identity), string transformation and tests (trim, upper, lower, contains, starts-with, ends-with, replace), the text spelling of a value as `print` writes it, checked integer absolute value, minimum and maximum, decimal integer parsing with a payload-free error, result predicates and unwraps, and checked conversion between signed integers and counts. A reference to an element or field of a local now borrows its owner with a real loan, so `&names[1]` and `&pair.right` work; a frozen constant that is a string or scalar lowers to the ordinary constant instructions. `modern.ya`, `tour.ya`, `generics.ya`, `parser.ya`, `postfix-dereference.ya`, `enums/patterns.ya`, `enums/result.ya`, `dfs.ya` and `gc-rc.ya` now run with the documented output, which makes 27 of the 33 examples identical to the old interpreter. The six that remain are `traits.ya` (trait objects), `secret-number.ya` and `input.psc` (interactive input), `managed.ya` (allocators), `locations.ya` (locations) and `lookups.ya` (lookup plans). Parse errors carry no message text, and only 64-bit integer parsing is supported.

Vectors, ranges and cells are implemented (format v20). They are identified by the traits and kinds their declarations carry (a collection that is not double-ended, a type with a dereferenced single argument, the range storage kind, the weak flag), not by declared names, so the earlier name shim for the weak reference is gone. A vector is a growable owned sequence indexed from zero with checked indices; `Vec::from(range)`, a literal, `push`, `len`, indexing, `sum` and slicing work, and growth is capped at 2^22 elements. A range is a pair of integers, stored half-open, so an inclusive range that ends at the maximum integer overflows with a typed error. A cell holds one value and is replaced through any loan, shared included, which is what interior mutability means; `read`, write and `replace` work. Records are interned by declared name and reserve their shape first, so a record can refer to itself through a handle, as `Node` does in `gc-cycles.ya`. `mergesort.ya`, `quicksort.ya`, `knapsack.ya`, `gc-cells.ya`, `gc-cycles.ya` and `gc-sharing.ya` run with the documented output, and cycles built through cells are collected. `managed.ya` (allocators), `locations.ya` (locations) and `lookups.ya` (lookup plans) need operations that are not implemented. Collections are provided by the engine itself here; moving them behind provider bindings in the registry is still the stage 9 migration. Double-ended vectors and the other collection operations (`pop`, `as_slice`) are not implemented.

Slices of arrays are implemented (format v19). A slice is a window onto the elements of a one-dimensional array that starts at zero; it exists only as the pointee of a loan, so `&[]T` and `&mut []T` parameters are loans whose place carries the window. `SliceOf` views an array, or another slice, through a loan with the root and access of its source, `SliceLength` and `Sum` read the window, and an element of a slice is borrowed with a checked, zero-based index relative to the window. The verifier rejects a slice held by value and viewing an array that does not start at zero. Sorting and reversing through `&mut []i64` on arrays work, including recursion that passes one view down every call. `mergesort`, `quicksort` and `knapsack` are still blocked, because they build their data with `Vec::from(range)`, which needs the SDK collections. Sub-slices (`a[lo..hi]`) and slices of `Vec` come with them.

Counted ownership is implemented (format v18). `rc T` owners and the standard weak reference are values with control blocks owned by the activation: `rc expr` allocates with one owner, clone adds an owner, downgrade adds a weak reference, upgrade returns an option holding a new owner while one lives, and strong count is an unsigned count. Releasing the last owner destroys the payload, cascading through what it owned, and a block is freed once no owner or weak reference remains. Real moves empty their source (`Move`, `EnumTake`), and a move out of a projected place, as when a match binds one field of a pair, leaves a hole that the later drop of the remainder skips (`MoveOut`). A drop of a value already moved out releases nothing, so scope-end drops of moved locals are fine. Payloads of live counted objects are collector roots, so a heap object held only by an owner survives. `examples/rc-ownership.ya` and `examples/enums/ownership.ya` run with the documented output, with and without `--gc-stress`, and the tests assert that no counted object is left at the end. Known limits: the verifier tracks initialization for moves and drops but does not prove every owner is released exactly once, because copies through references are count-neutral aliases in checked IR; gc objects that own counted values are not destroyed by the collector; the weak type is recognized by its declared name until opaque types come from provider bindings; unsigned counts support only copies and output.

GC handles are implemented in the interpreter (format v17). A `gc T` value is a handle into a heap owned by the activation; `gc expr` allocates, and `.*` borrows the object, as a loan rooted at the heap object, so reads, whole-value writes and projections reuse the loan machinery. Handles are indices, so a collection never changes what a handle means. A mark-sweep collection runs at allocation when the live count reaches a threshold (twice the survivors, at least 256), before every allocation under `--gc-stress`, and from every frame, module variable, closure capture, loan root and heap object. Recursive enums work: a handle is an indirection, so a shape may refer to itself through one, and the verifier now rejects only containment by value. Tuples, arrays and records are interned structurally, so two spellings of one type are one shape. `examples/enums/recursive.ya` runs with the documented output, with and without `--gc-stress`. Heap objects are immutable until `Cell` exists (the checker requires interior mutability), so unreachable cycles cannot be built yet; the collector traces them correctly and is tested through abandoned chains. Handles are native-ineligible and carry no native root maps yet.

Module-level variables are implemented (format v16). The cell locals of `<main>` that other routines reach through global slots become module variables held by the activation, each with a declared type. A routine borrows one with `BorrowGlobal`, which yields a loan whose root is the variable, so reads, whole-value writes, field projections and lending to other routines reuse the loan machinery. Reading a variable before `<main>` assigns it fails with a typed error. `examples/hot-loop.ya` and `examples/osr-loop.ya` now run on the verified engine with the documented output. Arrays and other uninitialized-at-declaration variables that are also globals are not initialized by lowering yet.

Step 4 is implemented (format v15, `examples/composites.ya` runs end to end under `--engine verified` and prints the documented lines). A closure that captures loans has its own register kind that behaves like a loan on the captured root: the root stays live and borrowed while the closure lives, an exclusive closure blocks reads of its owner, and liveness follows the chain of owners so a closure over a projected loan keeps the original owner alive. Such a closure can be copied between registers of the same kind, borrowed (`&mut increment`), and called, but not stored in a composite, passed by value or returned. A closure that captures loans from two different roots is refused when lowering. The callee side already received loan parameters, so `&mut proc()` is a loan whose pointee is the closure and calling it reads the closure through the loan. Capturing a field by loan (`proc[&mut c.hits]`) is not accepted by the parser.

Steps 1 and 2 are independent of 3 and 4. Steps 3 and 4 are the same mechanism that `rc`, `gc` and the `&mut` enum payload writes also need.

## Managed memory and stack switching in the verified pipeline

This section places garbage collection, reference counting and coroutine stack switching in the same plan, so that the `composites.ya` steps above are built compatibly. The language contracts are in [managed memory](managed-memory.md), [GC plan](gc-plan.md) and the [concurrency runtime](concurrency.md). The native recovery contract is in the [backend design](backend-design.md#images-publication-and-recovery). Items that depend on a pending decision are marked *open*.

### Value kinds the verified bytecode must distinguish

| Kind | Meaning | Storage rule |
| --- | --- | --- |
| Plain value | Scalar, text, tuple, record, enum or array with no handles and no destructor (today's slice) | Owned by its register. Copy is a clone. End of life is a no-op. |
| Owned value with drop obligations | A composite containing an `rc` owner or a value with a destructor | Moves are real: a moved-from register becomes uninitialized. End of life runs drop glue exactly once, including on failure edges. |
| Loan | A shared or exclusive borrow of a place | Names its owner by frame and register, never by machine address, so it survives frame relocation. |
| `gc` handle | A traced reference to a heap object of one shape | Copy preserves identity. Handles are indirect, so a moving collector can relocate objects. |
| `rc` owner / weak | A counted owner and its weak observer | Move transfers the owner. Clone adds a count. The last strong release commits before payload destruction, and a weak upgrade fails once destruction has started. |

Two shortcuts taken in the strings and arrays slice are valid only for plain values: `Take` lowered as a copy and `Drop` lowered as a no-op. Before any owned value with drop obligations is admitted, lowering must key both on a per-shape `needs_drop` fact and use real move and drop-glue instructions instead. That change is the first managed slice below.

### Shape facts to add now

Every shape gets two derived facts, computed by the verifier from its components and not trusted from the image: `has_handles` (contains a `gc` handle, directly or through a payload, an environment or an array element) and `needs_drop`. Both are false for everything supported today. Enum tracing visits only the active variant. Arrays visit initialized elements only. Closure environments are shapes, so they carry the same facts.

### Garbage collection

- A collection runs only at statepoints: allocation, calls, fuel boundaries and parking. The interpreter's frames are roots by construction, since each register's type says whether it holds handles.
- Add `gc` allocation, handle copy, and field read and write through a handle. Allocation evaluates operands once, roots them while acquiring storage, and releases everything exactly once on failure.
- The runtime owns the heap, collection and relocation. The bytecode states the operation, its effects and its failure edge. A collection never runs guest cleanup during tracing; discovered cleanup is queued as rooted work.
- Native adapters later consume the same facts to emit the GC-root and stack-relocation maps (stage 6A/6B). Nothing in the interpreter slice may assume a handle is a raw address.
- *Open:* whether the verified interpreter keeps one heap per coroutine (local by default) with explicit transfer, or a runtime heap with per-coroutine root sets. `@shared` stays a typed rejection until its runtime contract exists.

### Reference counting

- Add owner move, clone, release, downgrade and weak upgrade, and strong and weak counts. Moves end the source's initialization in the verifier, which then rejects use-after-move and double release.
- Drop glue is generated from the shape. Cleanup that can park is resumable at its own instruction boundary, and exactly once across failure and cancellation.
- Strong cycles are not collected, as the existing plan states. Counts, identity and allocator effects stay observable, as they are today.

### Stack switching and coroutines

- The verified interpreter already holds its frames as data and resumes after one instruction, so a coroutine park is a frame stack that is handed back to the scheduler and later resumed. Native code keeps the Go-style copying stacks from the backend design: stop exclusively, repair every recorded stack reference and the saved context, then resume.
- Parking is a bound call whose operation identity, destination and continuation are registered before submission. Lexical generator yield stays distinct from parking.
- A loan may live across a park inside the same coroutine, because it names its owner by frame and register. Nothing carrying a loan or a local managed value may be captured by a spawned task or sent through a channel. The verifier rejects it using the shape facts above.
- Frames must stay relocatable: no instruction may keep a raw pointer into a frame between statepoints.

### How each `composites.ya` step stays compatible

| Step | Compatibility requirement |
| --- | --- |
| 1. Records | Record shapes carry `has_handles` and `needs_drop` from the start. Field places are projections of an owner, not copies of an address. |
| 2. Function values | A closure value's environment is an owned shape built from an explicit capture plan (copy, move, borrow). Invocation borrows the environment and never clones every capture. The closure's call signature records whether it is repeatable, exclusive or consuming, so one-shot closures can be added without changing the encoding. |
| 3. Loans of any pointee | The loan rules cover handles and owners as well: an exclusive loan blocks moves, and no loan outlives a drop of its owner. Loan origins stay frame-and-register, never addresses. |
| 4. Loans inside values | A closure holding a loan keeps its owner pinned for the closure's life, including across a park in the same coroutine. Returning it and spawning with it are rejected. |
| 5. Whole example | Fuel pauses and one-instruction resume preserve every owned value and loan, the same property the managed slices rely on. |

### Managed slices after `composites.ya`

1. **Ownership states.** Real moves, drop glue and `needs_drop` for owned plain composites. Replace the `Take` and `Drop` shortcuts. Gate: scope exit, overwrite and failure paths release exactly once, with bounded frame storage.
2. **GC in the interpreter.** Heap, handles, roots, collection at statepoints, tracing of aggregates, enums and closure environments. Gate: `gc-cells.ya`, `gc-cycles.ya`, `gc-sharing.ya` and `enums/recursive.ya` under `--gc-stress`.
3. **RC.** Owners, weak references, counts, last-release ordering and parked cleanup. Gate: `gc-rc.ya`, `rc-ownership.ya` and `enums/ownership.ya`.
4. **Allocator-bound allocation.** Custom allocators with typed failure edges and cleanup that parks. Gate: the allocator fixtures.
5. **Coroutines in the interpreter.** Tasks, channels and bound calls that park, with cancellation and exactly-once host effects. Gate: the `examples/concurrency/` programs.
6. **Native recovery.** GC-root, stack-relocation, ownership and recovery maps for both adapters, copying stacks and loop OSR (stages 6B to 6D). Each map is tested independently before stack copying is enabled by default.

Slices 1 to 5 are interpreter work and need no native change. Slice 6 starts only after the interpreter conformance for the feature it covers. The cutover (stage 7A) is blocked until every shipping `.ya` example and the concurrency suite run on the verified pipeline. Output is native-ineligible and stays in the verified interpreter.
