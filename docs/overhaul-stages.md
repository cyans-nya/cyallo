# Compiler and SDK implementation stages

Deliver both overhauls as reviewable slices. The first shared proof is a fixture SDK bound call that runs through verified bytecode and uses an installed table in the verified interpreter. Lead with interpreter implementation and independent conformance. The compiler track can work on syntax and checked execution while the SDK track works on declarations and world loading. ## Dependencies and review checkpoints

- **Stage 0 → stage 1.** Start with the existing tree and release artifacts. The recorded no-compilation constraint still applies. Source inventory, test design and artifact inspection can proceed now. A build or executable verification gate that needs a new artifact remains pending until compilation is authorized.
- **Stages 2A and 2B can overlap.** Start stage 3 once the fixture resolves to an installed contract and the checked semantic adapter is available. Full AST conversion and complete world instantiation can continue alongside the interpreter slice. Finish AST parity before deleting its adapter.
- **Stage 4 has separate acceptance gates for layout and reuse.** Start the generic descriptor and reference layout before choosing inline shapes and niches. Keep physical reuse and cache retirement behind the scope release and loan decisions. Stage 5 can use reference layouts and bounded fixture inputs while that work is pending. Full scope correctness is required for cutover.
- **Interpreter conformance comes before stage 6.** Exercise resumable execution, the required storage and ownership contracts, and the first fixture bound call in the verified interpreter. Start native work against independently checked results and publish only functions with complete lowering and maps.
- **Check compacted scalar bytecode during stage 3.** Exercise relocated branches and backedges, and debugger markers at activation pauses. [No-op removal](backend-design.md#remove-executable-no-ops-before-interpreter-conformance)
- **Stages 7 and 8 share recovery metadata.** Start scheduler and bridge work once the image format is stable. Enable native stack copying only after all live stack references are accounted for. Enable loop OSR after import/export and commit-phase recovery work on an active frame.
- **Stage 9 is incremental.** Core supply, package migration, and removal of obsolete producers can land as their gates clear. Record deferred items individually. Resolving a public package choice does not change the verified bytecode or backend interface.
- **Stage 10 is a direct execution switch.** Implementation slices run independently before cutover. Test expectations come from language, runtime and SDK contracts. Any required operation the verified interpreter cannot execute blocks the switch. Native admission and recovery remain inside the new pipeline.

Before closing a stage, record the delivered behavior, exact revision/configuration, checks performed, and any skipped gate. Mark performance figures as measured or historical. Use the pending-decision records for authority on core, layout, source failure, SDK defaults, storage reuse, test remediation and repository policy. [Pending decisions](pending-decisions/README.md)

## First implementation slices

These slices are in the working tree following the data-enum baseline `d6ebc04` and the backend design revision `8e1cbef`. Release-profile runs cover the verified bytecode, CLI and scalar SDK fixtures. Workspace failures are tracked by name. [Regression record](pending-decisions/07-baseline-failures.md)

| Area | Working slice | Next integration gate |
| --- | --- | --- |
| AST | Ordinary source, REPL, file-graph and runtime module compilation now route user source through indexed syntax. File discovery uses indexed module declarations and passes its snapshots to compilation. Modern relinking retains static snapshots and materializes trees at the linker boundary. | Run parity, diagnostic and dynamic-load tests on the changed entry points and measure parse and check costs. Build tables directly during parsing and migrate core, resolution, generic instantiation and deferred checking before retiring the source-tree adapters. |
| Bytecode and interpreter | Opt-in verified scalar bytecode v8 with direct, bound and output call targets, the loop step check, explicit storage lifetimes, shared/exclusive scalar loans and borrowed calls. Programs that print integers, booleans and string constants run end to end: `cyallo run --engine verified` executes the entry routine and refuses anything it cannot lower before running. Format v9 adds composite registers: tuples and enums of scalars and nested composites, described by module shapes with an explicit variant index (the reference layout; inline shapes and niches stay with the layout decision). A composite owns its value and shares the register's storage lifetime, so loop rebuilds reuse one frame slot. Composites cross direct calls as parameters and results, but the entry routine stays scalar. Matching reads by value; payloads read by address are reference copies and writes through them, by-reference matches and loans of composites are refused. Composites are native-ineligible. Format v11 adds binary64 values (stored as bits), IEEE float arithmetic and comparison, checked integer and float negation, boolean `not` and equality, `i64`/`f64` conversion with typed out-of-range failure, and integer real division for CAIE `/`. Float output uses the shortest round-trip spelling. Float routines are native-ineligible. Format v12 adds immutable strings (`text`) and fixed-size arrays with inclusive per-dimension bounds, elements that start uninitialized when declared, checked indices, and character-based `len`/`LEFT`/`RIGHT`/`MID` with typed failures. Arrays are limited to 2^22 elements by the verifier. Text and arrays are native-ineligible. Mixed integer/real operands, other numeric widths, globals, records, function values and closures, loans of non-scalars, owned payloads (`rc`, `gc`), growable collections and tasks remain unsupported and block cutover (stage 6A). Priority is the Cyallo (`.ya`) language; CAIE support is incidental.

**Roadmap to run `examples/composites.ya`** (records, tuples of records and closures, by-value and by-reference closure capture):

1. *Records.* A record is a named-field tuple shape. Lower `Type::Record` to a shape and project nested fields (`pair.0.x`) as field-of-field places. Gate: `Point` fields print through a tuple.
2. *Function values and by-value capture.* A closure value is a composite of a routine id and captured values. Add a closure value type that carries its call signature, a construct instruction, and an indirect call that the verifier checks against the signature. Checked IR passes captures as leading parameters of the closure routine. Gate: `apply(offset_by(3), 4)` prints 7 and a closure survives being returned.
3. *Loans of any pointee.* Generalize loans beyond scalars to composites and closures, with the owner-lifetime and conflict rules the scalar loans already have. Gate: `&mut` and `&` parameters of tuples and records read and write fields in place.
4. *Loans stored inside values.* A closure may capture a mutable loan (`proc[&mut count]`). The verifier must keep the owner live and exclusive for as long as the closure value lives, and reject returning it. Add an indirect call through a loan to a closure. Gate: `count_twice()` prints 2 and the escaping variant is rejected.
5. *Gate for the whole example.* Output equals the documented lines under the verified engine, with typed failures and fuel preserved across pauses.

**Status.** Steps 1 and 2 are implemented (format v13). Records lower to named-field tuple shapes that keep their declaration identity, and nested field reads (`pair.0.x`) lower to value extracts. Closures are values with a module signature table, a construct instruction whose captures become the routine's leading parameters, and an indirect call checked against the signature. Closures work as parameters, results, tuple, record and array elements, and capture scalars, text and composites by value. Closures and records are native-ineligible. `composites.ya` runs completely on the verified pipeline. Writes through a field or payload address are still refused, since the register holds a copy.

Step 3 is implemented (format v14). A loan now carries its pointee type, so it can borrow a value of any type: scalar, text, tuple, record, enum, array or closure. Whole-value reads and replacement go through `ReadLoan` and `WriteLoan`. A loan can be projected to one field, enum payload or array element, from an owner or from another loan, and the projected loan keeps the root's origin and never has wider access than its base. Projected places are paths from the owning register, so they stay valid when frames move. The verifier rejects a projection whose pointee or access does not match its base, and rejects reading or reborrowing the owner while an exclusive projection lives. Reads from a local's field or payload still observe a copy, and writes through a local's field, nested field, loan parameter or projected loan are real in-place writes. Writes through a copy are refused when lowering. Projecting into a variant that is not held fails with a typed error.

GC handles are implemented in the interpreter (format v17). A `gc T` value is a handle into a heap owned by the activation; `gc expr` allocates, and `.*` borrows the object, as a loan rooted at the heap object, so reads, whole-value writes and projections reuse the loan machinery. Handles are indices, so a collection never changes what a handle means. A mark-sweep collection runs at allocation when the live count reaches a threshold (twice the survivors, at least 256), before every allocation under `--gc-stress`, and from every frame, module variable, closure capture, loan root and heap object. Recursive enums work: a handle is an indirection, so a shape may refer to itself through one, and the verifier now rejects only containment by value. Tuples, arrays and records are interned structurally, so two spellings of one type are one shape. `examples/enums/recursive.ya` runs with the documented output, with and without `--gc-stress`. Heap objects are immutable until `Cell` exists (the checker requires interior mutability), so unreachable cycles cannot be built yet; the collector traces them correctly and is tested through abandoned chains. Handles are native-ineligible and carry no native root maps yet.

Module-level variables are implemented (format v16). The cell locals of `<main>` that other routines reach through global slots become module variables held by the activation, each with a declared type. A routine borrows one with `BorrowGlobal`, which yields a loan whose root is the variable, so reads, whole-value writes, field projections and lending to other routines reuse the loan machinery. Reading a variable before `<main>` assigns it fails with a typed error. `examples/hot-loop.ya` and `examples/osr-loop.ya` now run on the verified engine with the documented output. Arrays and other uninitialized-at-declaration variables that are also globals are not initialized by lowering yet.

Step 4 is implemented (format v15, `examples/composites.ya` runs end to end under `--engine verified` and prints the documented lines). A closure that captures loans has its own register kind that behaves like a loan on the captured root: the root stays live and borrowed while the closure lives, an exclusive closure blocks reads of its owner, and liveness follows the chain of owners so a closure over a projected loan keeps the original owner alive. Such a closure can be copied between registers of the same kind, borrowed (`&mut increment`), and called, but not stored in a composite, passed by value or returned. A closure that captures loans from two different roots is refused when lowering. The callee side already received loan parameters, so `&mut proc()` is a loan whose pointee is the closure and calling it reads the closure through the loan. Capturing a field by loan (`proc[&mut c.hits]`) is not accepted by the parser.

Steps 1 and 2 are independent of 3 and 4. Steps 3 and 4 are the same mechanism that `rc`, `gc` and the `&mut` enum payload writes also need.

## Managed memory and stack switching in the verified pipeline

This section places garbage collection, reference counting and coroutine stack switching in the same plan, so that the `composites.ya` steps above are built compatibly. The language contracts are in [managed memory](managed-memory.md), [GC plan](gc-plan.md) and the [concurrency runtime](concurrency.md). The native recovery contract is in the [backend design](backend-design.md#images-publication-and-recovery). Items that depend on a pending decision are marked *open*.

### Value kinds the verified bytecode must distinguish

| Kind | Meaning | Storage rule |
| --- | --- | --- |
| Plain value | Scalar, text, tuple, record, enum or array with no handles and no destructor (today's slice) | Owned by its register. Copy is a clone. End of life is a no-op. |
| Owned value with drop obligations | A composite containing an `rc` owner or a value with a destructor | Moves are real: a moved-from register becomes uninitialized. End of life runs drop glue exactly once, including on failure edges. |
| Loan | A shared or exclusive borrow of a place | Names its owner by frame and register, never by machine address, so it survives frame relocation. |
| `gc` handle | A traced reference to a heap object of one shape | Copy preserves identity. Handles are indirect, so a moving collector can relocate objects. |
| `rc` owner / weak | A counted owner and its weak observer | Move transfers the owner. Clone adds a count. The last strong release commits before payload destruction, and a weak upgrade fails once destruction has started. |

Two shortcuts taken in the strings and arrays slice are valid only for plain values: `Take` lowered as a copy and `Drop` lowered as a no-op. Before any owned value with drop obligations is admitted, lowering must key both on a per-shape `needs_drop` fact and use real move and drop-glue instructions instead. That change is the first managed slice below.

### Shape facts to add now

Every shape gets two derived facts, computed by the verifier from its components and not trusted from the image: `has_handles` (contains a `gc` handle, directly or through a payload, an environment or an array element) and `needs_drop`. Both are false for everything supported today. Enum tracing visits only the active variant. Arrays visit initialized elements only. Closure environments are shapes, so they carry the same facts.

### Garbage collection

- A collection runs only at statepoints: allocation, calls, fuel boundaries and parking. The interpreter's frames are roots by construction, since each register's type says whether it holds handles.
- Add `gc` allocation, handle copy, and field read and write through a handle. Allocation evaluates operands once, roots them while acquiring storage, and releases everything exactly once on failure.
- The runtime owns the heap, collection and relocation. The bytecode states the operation, its effects and its failure edge. A collection never runs guest cleanup during tracing; discovered cleanup is queued as rooted work.
- Native adapters later consume the same facts to emit the GC-root and stack-relocation maps (stage 6A/6B). Nothing in the interpreter slice may assume a handle is a raw address.
- *Open:* whether the verified interpreter keeps one heap per coroutine (local by default) with explicit transfer, or a runtime heap with per-coroutine root sets. `@shared` stays a typed rejection until its runtime contract exists.

### Reference counting

- Add owner move, clone, release, downgrade and weak upgrade, and strong and weak counts. Moves end the source's initialization in the verifier, which then rejects use-after-move and double release.
- Drop glue is generated from the shape. Cleanup that can park is resumable at its own instruction boundary, and exactly once across failure and cancellation.
- Strong cycles are not collected, as the existing plan states. Counts, identity and allocator effects stay observable, as they are today.

### Stack switching and coroutines

- The verified interpreter already holds its frames as data and resumes after one instruction, so a coroutine park is a frame stack that is handed back to the scheduler and later resumed. Native code keeps the Go-style copying stacks from the backend design: stop exclusively, repair every recorded stack reference and the saved context, then resume.
- Parking is a bound call whose operation identity, destination and continuation are registered before submission. Lexical generator yield stays distinct from parking.
- A loan may live across a park inside the same coroutine, because it names its owner by frame and register. Nothing carrying a loan or a local managed value may be captured by a spawned task or sent through a channel. The verifier rejects it using the shape facts above.
- Frames must stay relocatable: no instruction may keep a raw pointer into a frame between statepoints.

### How each `composites.ya` step stays compatible

| Step | Compatibility requirement |
| --- | --- |
| 1. Records | Record shapes carry `has_handles` and `needs_drop` from the start. Field places are projections of an owner, not copies of an address. |
| 2. Function values | A closure value's environment is an owned shape built from an explicit capture plan (copy, move, borrow). Invocation borrows the environment and never clones every capture. The closure's call signature records whether it is repeatable, exclusive or consuming, so one-shot closures can be added without changing the encoding. |
| 3. Loans of any pointee | The loan rules cover handles and owners as well: an exclusive loan blocks moves, and no loan outlives a drop of its owner. Loan origins stay frame-and-register, never addresses. |
| 4. Loans inside values | A closure holding a loan keeps its owner pinned for the closure's life, including across a park in the same coroutine. Returning it and spawning with it are rejected. |
| 5. Whole example | Fuel pauses and one-instruction resume preserve every owned value and loan, the same property the managed slices rely on. |

### Managed slices after `composites.ya`

1. **Ownership states.** Real moves, drop glue and `needs_drop` for owned plain composites. Replace the `Take` and `Drop` shortcuts. Gate: scope exit, overwrite and failure paths release exactly once, with bounded frame storage.
2. **GC in the interpreter.** Heap, handles, roots, collection at statepoints, tracing of aggregates, enums and closure environments. Gate: `gc-cells.ya`, `gc-cycles.ya`, `gc-sharing.ya` and `enums/recursive.ya` under `--gc-stress`.
3. **RC.** Owners, weak references, counts, last-release ordering and parked cleanup. Gate: `gc-rc.ya`, `rc-ownership.ya` and `enums/ownership.ya`.
4. **Allocator-bound allocation.** Custom allocators with typed failure edges and cleanup that parks. Gate: the allocator fixtures.
5. **Coroutines in the interpreter.** Tasks, channels and bound calls that park, with cancellation and exactly-once host effects. Gate: the `examples/concurrency/` programs.
6. **Native recovery.** GC-root, stack-relocation, ownership and recovery maps for both adapters, copying stacks and loop OSR (stages 6B to 6D). Each map is tested independently before stack copying is enabled by default.

Slices 1 to 5 are interpreter work and need no native change. Slice 6 starts only after the interpreter conformance for the feature it covers.
